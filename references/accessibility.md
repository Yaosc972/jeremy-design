# 无障碍设计（Accessibility）

> 来源: https://developer.apple.com/design/human-interface-guidelines/accessibility
> 整理自 Apple HIG 原文（2026-09 抓取）。规范条目忠实原文，未新增规则。

## 概述

为无障碍设计能触达更多用户，创造更包容的体验。无障碍界面让任何人——无论能力如何、如何使用设备——都能体验你的 app 或游戏。一个无障碍界面应具备：

- **直观（Intuitive）。** 界面使用熟悉且一致的交互，让任务执行起来直接明了。
- **可感知（Perceivable）。** 界面不依赖任何单一方式传达信息。无论用户使用视觉、听觉、语音还是触觉，都能访问并与内容交互。
- **可适应（Adaptable）。** 界面适应用户想要的设备使用方式——支持系统无障碍功能，或允许用户个性化设置。

设计 app 时，审计界面的无障碍性：使用 **Accessibility Inspector** 高亮界面问题、了解 app 如何向使用系统无障碍功能的用户呈现自己；可在 App Store 通过 **Accessibility Nutrition Labels** 说明 app 的无障碍支持情况。

## Vision（视觉）

界面用户可能是盲人、色盲、低视力或光敏感人群；也可能处于光线条件与屏幕亮度影响操作的环境中。

- **支持更大的文本尺寸。** 确保用户可调整文本或图标大小使其更清晰易读。理想情况下，允许用户至少放大文本 **200%**（watchOS app 为 **140%**）。可通过自定义 UI 或采用 Dynamic Type（系统级设置）支持字号放大。参见 Typography。
- **自定义字号采用推荐默认值。** 各平台系统定义的字体样式有不同的默认和最小字号。使用自定义字体样式时请遵循：

| 平台 | 默认字号 | 最小字号 |
|---|---|---|
| iOS, iPadOS | 17 pt | 11 pt |
| macOS | 13 pt | 10 pt |
| tvOS | 29 pt | 23 pt |
| visionOS | 17 pt | 12 pt |
| watchOS | 16 pt | 12 pt |

- **注意字重也影响文本易读性。** 使用细字重（thin weight）自定义字体时，字号应大于推荐值。
- **努力满足颜色对比度最低标准。** 前景文本/图标与背景色之间需有足够对比度。常用标准为 [WCAG](https://www.w3.org/TR/WCAG/) 和 APCA（Accessible Perceptual Contrast Algorithm）。Accessibility Inspector 以 WCAG AA 级以下数值为判定指导：

| 文本字号 | 文本字重 | 最低对比度 |
|---|---|---|
| 17 pt 及以下 | 全部 | 4.5:1 |
| 18 pt | 全部 | 3:1 |
| 全部 | 加粗（Bold） | 3:1 |

  ⚠️ **Web 实现注意（Apple 页面与 WCAG 的冲突）**：上表忠实摘自 Apple Accessibility 页，其中"Bold 任意字号 3:1"与 W3C WCAG 对网页文字的判定**不一致**。WCAG AA 中普通文字（包括小字号粗体）一律 ≥4.5:1，仅"大号文字"放宽到 3:1——通常为 ≥24 CSS px 的常规字重，或 ≥约 18.67 CSS px 的粗体。实现网页时按 W3C WCAG 的字号与字重条件验收，**不能据此把所有粗体文字的阈值降到 3:1**；实现原生 Apple 平台界面时按上表。

  若 app 默认达不到此最低对比度，必须确保开启系统设置 **Increase Contrast** 时至少提供更高对比度的配色方案。若 app 支持 Dark Mode，亮色和暗色两种外观下都要检查最低对比度。
- **优先使用系统定义颜色。** 这些颜色自带无障碍变体，会随用户颜色偏好（Increase Contrast、亮/暗外观切换）自动适配。参见 Color。
- **不要仅靠颜色传达信息。** 部分用户难以区分某些颜色（如红绿、蓝橙搭配）。除颜色外，还应提供视觉指示（不同的形状或图标）帮助用户感知功能差异与状态变化。可考虑允许用户自定义配色（如图表颜色、游戏角色颜色）。
- **为 VoiceOver 描述 app 界面与内容。** VoiceOver 是让用户不看屏幕即可体验 app 的屏幕阅读器。参见 VoiceOver。

## Hearing（听觉）

界面用户可能是聋人或听障人士，也可能处于嘈杂或公共环境中。

- **支持以文本方式欣赏音频与视频。** 对话和关键信息不能只通过音频传达，并允许用户自定义文本的视觉呈现：
  - **Captions（字幕/说明文字）**：为视频或纯音频内容中可听到的信息提供文字等价物，适合与媒体实时同步的场景（如游戏过场、视频片段）。
  - **Subtitles（翻译字幕）**：让用户以偏好语言阅读屏幕上的实时对话，适合电视剧和电影。
  - **Audio descriptions（音频描述）**：插入视频主音频的自然停顿处，口述仅以视觉呈现的重要信息。
  - **Transcripts（完整文稿）**：提供覆盖听觉与视觉信息的完整文字描述，适合播客、有声书等长内容。
- **在音频提示之外提供 haptics（触感反馈）。** 若界面通过音频提示传达信息（成功提示音、错误音、游戏反馈等），应为听不到或关闭声音的用户配以匹配的触感反馈。iOS/iPadOS 还可用 Music Haptics 和 Audio graphs 让用户通过振动体验音乐和信息图。参见 Playing haptics。
- **用视觉线索增强音频提示。** 对游戏和空间类 app 尤其重要——重要内容可能发生在屏幕外。用音频引导用户执行操作时，同时添加指向交互位置的视觉指示。

## Mobility（行动能力）

确保界面为手部灵活性或行动受限的用户提供舒适体验。

- **提供尺寸足够的控件。** 过小的控件让许多用户难以点击与选择。务必达到各平台推荐的最小控件尺寸：

| 平台 | 默认控件尺寸 | 最小控件尺寸 |
|---|---|---|
| iOS, iPadOS | 44x44 pt | 28x28 pt |
| macOS | 28x28 pt | 20x20 pt |
| tvOS | 66x66 pt | 56x56 pt |
| visionOS | 60x60 pt | 28x28 pt |
| watchOS | 44x44 pt | 28x28 pt |

- **控件间距与尺寸同等重要。** 元素之间留出足够间距，降低误触概率。一般而言，带 bezel（边框）的元素四周约加 **12 pt** 间距；不带 bezel 的元素在可见边缘四周约 **24 pt** 间距。
- **常见交互支持简单手势。** 无论是否有残障，复杂手势对许多用户都有挑战。高频交互应使用最简单的手势——避免自定义的多指、多手手势，让重复操作既舒适又易记。
- **为手势提供替代方案。** 确保 UI 核心功能可通过不止一种物理交互方式完成。手势对行动不便用户可能不舒适，应提供屏幕上的等效操作。例如用滑动手势关闭视图时，同时提供按钮让用户可以点击或用辅助设备操作。
- **让用户通过 Voice Control 口头下达指令与输入信息。** Voice Control 下用户可完全用语音命令操作设备（执行手势、操作屏幕元素、听写编辑文本等）。为确保体验顺畅，须为界面元素正确标注标签。
- **集成 Siri 和 Shortcuts，让用户仅凭语音执行任务。** 用户可从 Siri、iPhone/Apple Watch 的 Action button、主屏幕快捷指令或控制中心发起自动化任务。参见 Siri。
- **支持与行动能力相关的辅助技术。** VoiceOver、AssistiveTouch、Full Keyboard Access、Pointer Control、Switch Control 等为行动不便用户提供替代交互方式。必须测试验证 app 支持这些技术，且界面元素标签标注恰当。

## Speech（言语）

Apple 的无障碍功能帮助有言语障碍或偏好文本交互的用户用设备有效沟通。

- **让用户仅用键盘导航和操作 app。** 用户可开启 Full Keyboard Access 用物理键盘导航；系统还定义了无障碍键盘快捷键及大量常用快捷键。**避免覆盖系统定义的键盘快捷键**，并测试 app 与 Full Keyboard Access 的配合。参见 Keyboards。
- **支持 Switch Control。** Switch Control 让用户通过独立硬件、游戏控制器或声音（如咔哒声）控制设备。app 支持后，用户可用它执行选择、点击、打字、绘制等操作。

## Cognitive（认知）

减少 app 的复杂性对所有用户都有益。

- **保持操作简单直观。** 确保用户可用易记、一致的交互完成导航。优先使用用户已熟悉的系统手势和行为，避免创造需要学习记忆的自定义手势。
- **尽量少用限时消失的界面元素。** 定时自动消失的视图和控件，对需要更长时间处理信息的用户、以及需要更多时间遍历界面的辅助技术用户是障碍。优先用明确的操作关闭视图。
- **考虑在游戏中提供难度调节。** 支持自定义难度，如降低通关条件、调整反应时间、开启操作辅助。
- **让用户控制音频与视频播放。** **避免在未提供播放控制的情况下自动播放音频和视频**。控制项须可发现、易于操作，并考虑提供全局设置让用户禁止自动播放。
- **允许用户关闭视频中的闪烁灯光。** 提供 Dim Flashing Lights（调暗闪烁灯光）设置响应：系统会计算、缓解并告知用户媒体中的闪烁。支持视频播放的 app 必须对该设置做出正确响应。
- **谨慎使用快速移动和闪烁动画。** 过度使用会分散注意力、引起头晕，甚至诱发癫痫。易感人群会开启 Reduce Motion 设置——该设置开启时，app 必须减少自动和重复的动画，包括缩放（zooming/scaling）和周边运动。其他减动效实践：
  - 收紧动画 spring 减少弹跳
  - 让动画直接跟随用户手势
  - 避免对 z 轴层级的深度变化做动画
  - 用淡入淡出（fade）替代 x/y/z 轴位移动画
  - 避免做进出模糊（blur）的动画
- **为 Assistive Access 优化 app UI。** Assistive Access 是 iOS/iPadOS 无障碍功能，为认知障碍用户提供 app 的精简版本（系统会设置降低认知负荷的默认布局与控件呈现）。开启该模式时遵循：
  - 识别 app 核心功能，移除非关键流程和 UI 元素。
  - 拆分多步流程，让用户每屏专注单一交互。
  - 执行难以恢复的操作（如删除文件）时，**必须请求两次确认**。

## Platform considerations

iOS、iPadOS、macOS、tvOS、watchOS 无额外考虑。

### visionOS

visionOS 提供头与手 Pointer Control、Zoom 等无障碍功能。

- **优先保证舒适。** 沉浸式特性下，界面、动画与交互更容易引起晕动症和视觉、工效不适。为获得最舒适的体验：
  - 界面元素保持在人的视野内。优先水平布局而非可能引起颈部疲劳的垂直布局；避免要求视线在不同位置间快速切换。
  - 降低动画物体的速度与强度，尤其是视野边缘的动画。
  - 相机与视频运动要温和，避免让用户感觉周围世界在不受控地移动。
  - 避免将内容锚定在佩戴者头部——会让用户感到被困住，也妨碍其使用 Pointer Control 等辅助技术。
  - 减少对大幅、重复手势的需求——这类手势易疲劳，且受环境限制可能难以完成。

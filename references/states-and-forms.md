# 状态与业务交互（列表 / 保存 / 表单）

> **性质**：`PROJECT-DEFAULT` 工程约定。SKILL.md 要求"实现正常、交互、异常三态"——本文件把这三类**按组件类型展开成具体状态清单**。控件本身的规范见 `components-controls.md`；无障碍关联见 `accessibility.md`。

## 0. 底线约束

> **每个可见操作都应有可验证的结果**；未接入真实服务时，**明确模拟边界**，不用假成功掩盖未实现功能。

按钮点了没反应、提交"成功"但数据没变、"待接入"的功能不给任何提示——都是交付缺陷。模拟数据要标注（如"演示数据"角标或明确告知用户），不伪装成真实完成。

## 1. 数据列表：六种状态缺一不可

| 状态 | 呈现要求 |
|---|---|
| **加载中** | 骨架屏/占位（优于转圈）；布局稳定不跳动 |
| **首次无数据** | 说明这是什么 + 引导创建的第一个操作 |
| **筛选/搜索无结果** | 显示生效条件 + "清除筛选"入口（不引导"新建"） |
| **加载失败** | 错误说明（可读的原因）+ **重试按钮**；不清空已有内容 |
| **部分成功** | 批量操作里部分失败：明示哪几条失败、原因、可否重试；成功项不重做 |
| **无权限** | 说明需要什么权限、向谁申请；不显示"空列表"（空列表会误导为"没有数据"） |

关键区分：**空 ≠ 错 ≠ 无权限**。三者文案与操作入口完全不同，混用会让用户误解数据状态。

## 2. 保存操作：全生命周期

- **未修改 / 已修改**：有未保存修改时离开页面（路由跳转、关闭标签）要拦截提示——用 `beforeunload`（浏览器限制只能默认文案）或应用内确认对话框。
- **提交中**：按钮进入 loading 并**禁用重复提交**；保留页面其余可交互部分（不要整页蒙层除非必须）。
- **提交失败**：**保留用户输入**（这是最重要的一条）；错误就地显示 + 可重试；网络类失败说明"内容已保留，可重试"。
- **保存成功**：反馈要有时点感（toast/就地提示，2–4 秒自动消退），说明保存了什么；连续编辑场景不打断后续操作。
- 自动保存（autosave）适用时：明确显示保存状态（"已保存 14:30" / "正在保存…"），失败时不能静默。

## 3. 表单：标签、说明、校验、错误、反馈

**标签**
- 每个输入有**可见的 `<label>`**（`for`/`id` 关联）；placeholder 是**补充示例**，不是标签的替代（placeholder 输入后消失）。
- 必填/可选要明示（全局约定 + 例外标注，比每个都加星号更干净）。

**帮助说明**
- 格式要求（"8–16 位，含字母和数字"）放在输入前或输入下常显；不要等出错才告诉用户规则。

**校验时机**
- **失焦时**校验该字段（用户完成了一次输入动作）；
- **提交后**整体校验并聚焦第一个错误字段；
- **输入中不打断**（输入过程中不弹错——尤其中文输入法合成期间）；字段合法后即时清除已有错误。
- 校验规则前后端一致；前端放宽后端拒绝时，错误信息必须可读（不是裸的 500）。

**错误关联（无障碍必需）**
- 错误文本与控件用 `aria-describedby` 关联 + `aria-invalid="true"`；
- 错误**不只靠红色**：图标 + 文本 + （可选）边线，三者至少两项（色觉障碍，`accessibility.md`）；
- 错误信息说**怎么改**（"邮箱缺少 @ 符号"），不只说"输入无效"；
- 错误摘要（字段多的长表单）：提交后在表单顶部给摘要，锚点跳转到对应字段。

**提交后反馈**
- 成功：给出明确去向（"已创建，正在进入详情…"或停在当前页并更新状态）；
- 失败：停留在表单、保留输入、错误可见（§2）；
- 提交按钮的文案反映动作（"创建项目"而非"提交"）。

## 4. 破坏性操作

- 确认对话框说明**影响范围与不可逆性**（"删除 24 项？此操作不可恢复"）；对高损失操作要求输入确认词（如项目名）而非简单"确定"。
- 提供撤销优于要求确认（如删除后可撤销 toast，时限 5–10 秒）——适用时优先。

## 5. 与验收的关系

- §1 的六种数据状态纳入 `detail-audit.md` 验收矩阵的"数据状态"维度逐个过检。
- 键盘与读屏验收：错误关联（`aria-describedby`/`aria-invalid`）、焦点管理（提交后聚焦第一个错误；成功后的去向焦点）在 `detail-audit.md` 的键盘档中实测。

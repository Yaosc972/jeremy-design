# 现有界面改版检查

适用于整页视觉改版、全局 CSS 替换和公共组件重做。只覆盖受影响且产品已有的界面；新建页面无需虚构旧版，局部修复不扩成全站审计。遵循用户指定的浏览器和项目工具。

## 1. 基线与样板

先保存原版代表状态，再实施。保持角色、数据、筛选、视口、缩放和滚动位置一致，等待字体与过渡稳定；只有新版截图不能证明改版有收益。无法运行原版时保留源文件并说明比较缺口。

按布局与组件差异选样板，而非只选最漂亮的页面：内容首页、密集列表、复杂表单、摘要卡片及浮层按实际存在情况覆盖。共享组件至少在最拥挤的使用场景验证一次。样板通过后扩展；公共规则改变后重查受影响的页面类型，不要求机械重复全部页面。

## 2. CSS 也是行为契约

改公共规则前查看其静态和动态使用处，尤其是以下关系：

- **真实 DOM 与选择器。** JS 可能把状态类加在根节点，而 CSS 期待子容器；对照运行时生成的结构，不凭类名清单猜结构。
- **默认态与显隐。** 记录哪个元素默认可见、由谁设置 `hidden`、`display` 或状态类。常驻提示不能改成“等待 JS 加类才显示”；关闭时也不能只禁用点击却保留可见文字。
- **上下文与级联。** 表单全宽输入规则不能无区别套到工具栏的短月份选择器；通用次要文字色不能覆盖深底卡片上的可读文字色。检查实际 computed style 和行内覆盖。
- **布局容器。** 网格列数由可用宽度与内容决定；先查子项最小宽度、flex 收缩和换行，再改字号。不要为了无页面横滚把局部内容挤成单字竖排。

保留 DOM、ID、变量或原 JS 只是兼容线索；必须通过渲染和操作确认。全量 CSS 重写时按相关组件记录简短的“旧结构/状态 → 新规则 → 实测结果”，无需为局部改动另写大文档。

## 3. 代表状态与通过条件

| 检查对象 | 实际操作与观察 | 不能当作通过的证据 |
|---|---|---|
| 静态提示、警告、错误 | 与原版同角色同状态比较，确认必要内容仍可见、权重明确；主动精简说明时保留所需信息与可发现入口 | DOM 里还有文字；元素隐藏后检测器无告警 |
| 筛选、表格、摘要卡片 | 比较工具栏高度、首屏可比较数据、长标题与状态标签；数值按列可比较，局部内容不越界 | 页面 `scrollWidth` 正常；所有类名都有定义 |
| 表单 | 检查字段分组、长标签、输入宽度及错误关联；调整列数须有实际收益 | 列数越多越高效，或必须保留原列数 |
| Toast / 临时反馈 | 经真实入口触发，检查出现位置、实际文案，再等待约定时长或执行关闭；确认消失且不留遮挡 | 调用过函数、计时器结束或 `.show` 已移除 |
| 模态弹窗 | 从入口打开，焦点进入弹窗，Tab/Shift+Tab 不进入背景；检查关闭方式与焦点返回，并核对对话框名称和语义 | 能按 Esc；给所有节点批量添加 tabindex |
| 非模态面板 | 检查焦点顺序、背景仍可操作的设计是否符合任务；不要误套模态焦点锁定 | 外形像抽屉，所以一律加焦点陷阱 |
| 响应式导航 | 在发生布局变化的断点两侧及目标窄窗口实际进入另一个模块，再进入子页；折叠后的菜单能辨认、能展开 | 侧栏宽度缩小就是“图标模式”；隐藏侧栏等于完成响应式 |

直接调用内部函数可以建立截图状态，但不证明用户能找到并操作入口。交互验收使用实际入口；模拟或未覆盖部分单独标注。无须为了验收触发真实业务写入。

## 4. 前后比较与交付

截图判断口径与可选工具见 [细节审查 §四](detail-audit.md#四视觉重构验收布局或视觉系统改版时使用)。重点回答：变清楚了什么、保留了什么、增加了哪些操作成本，而非仅描述换了什么颜色。

按代表页面/状态记录：`前后截图或位置 | 视觉结果 | 交互结果 | 问题与处置`。视觉和交互分别标为通过、需修复或未验证；已知旧问题与新增退化分开。截图数量、语法通过、控制台零错误、几何零阻断均不能替代这两项结果。

确认必要提示丢失、内容不可读、反馈无法关闭或导航不可达时，不得用“风格取舍”备案为通过。修复后复查相关状态；环境受限或仍有问题则如实交付未完成范围，不称“功能无损”或“全部通过”。这些检查由执行者完成，不新增用户审批环节。
